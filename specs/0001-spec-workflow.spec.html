Developing at the spec level

A project has a specs/ folder that holds what "green" means here and the specs written against it — so run-spec starts warm instead of re-deriving the same facts every run, and reads its register instead of guessing it out of prose.

Today

  • run-spec is a single skill: SKILL.md, reference/register.md, scripts/runspec.py (627 lines, standard library only). Subcommands are init · where · status · dash · list · active — runspec.py:612
  • Tick 0 re-derives the same project facts every single run. The gate is guessed from package.json/pyproject.toml/Cargo.toml/go.mod/Makefile — guess_gate(), runspec.py:93, and the worktree recipe is derived against a throwaway worktree by hand — SKILL.md, tick 0 steps 3–5. Both are properties of the project, not of the run.
  • The register is derived from prose by the model. There is no parser: nothing in runspec.py reads a spec file. cmd_init writes "criteria": [] and the model fills it — runspec.py:121. The most expensive step of tick 0 is also the least reproducible one.
  • The dashboard's design tokens live inline in runspec.py:333–441. There is no second consumer yet, so nothing has drifted — and nothing prevents it either.
  • Corrected against measurement. This originally read: "on this machine ~/.claude/skills/run-spec is a real directory holding an older German SKILL.md, not a symlink". It was — and was cleared and re-linked on 2 Sep 00:55, while this spec was being written. stat now reports the same inode for both SKILL.md paths. The claim was true when written and false two hours later, which is the ordinary lifespan of a fact about someone's machine: the criterion below no longer asserts it, it constructs it.
  • Nothing about a specs folder exists. This spec is the first file in one.

Not in this scope

  • Run state stays outside the project, under ~/.claude/runs/<project>/<run>/. The specs folder holds source, not state.
  • Markdown specs keep working. HTML is the format /new-spec writes, not a requirement run-spec imposes.
  • No web UI, no server, no build step. A spec is one file you can open by double-clicking it.
  • The tick itself — harvest, reconcile, dispatch — is not changed here beyond where tick 0 gets its facts from.

A · The project learns what green means

spec-init6 criteria

  • In a project without one, /spec-init leaves behind a specs folder that explains itself, and running it twice changes nothing.

    Check After /spec-init in a git repo with no specs/: specs/spec.config.json and specs/README.md exist and git status --short lists exactly those two as untracked. The README names the config's fields and the two commands.

    Counter A second /spec-init writes no file — specs/spec.config.json keeps its mtime — and says the folder already exists.

  • The gate in the config was measured, not guessed — and a red gate is recorded as red rather than rounded up.

    Check spec.config.json holds a non-empty gate and an integer expected_gate_pass. Running that gate command in the main tree reproduces exactly that number.

    Counter In a project whose gate is already red, expected_gate_pass is null and gate_status is "red" with the first failure's text. No green number is invented.

  • The worktree recipe is what actually closed the gap, in the order it closed it.

    Check git worktree add --detach /tmp/probe HEAD, then the commands in worktree_recipe[] verbatim, then the gate — the pass count equals expected_gate_pass. Each entry carries the error that made it necessary.

    Counter In a project whose fresh worktree is green untouched, worktree_recipe stays [] — it is not filled with an install that proves nothing.

  • What the gate does not cover is written down next to it.

    Check gate_gaps[] names every check the gate command does not run — typecheck under a transpiling runner (tsx, ts-node, swc, babel-jest), lint, format — one sentence each, with whether the missing check is currently clean.

    Counter A check the gate already runs does not appear in gate_gaps. On a project whose gate is test && tsc --noEmit, typecheck is absent from the list.

  • Tick 0 reads the configuration instead of re-deriving it, and says where its numbers came from.

    Check With specs/spec.config.json present, tick 0 skips steps 3–5 and copies gate, expected_gate_pass and worktree_recipe into run.json verbatim; the tick report names the config file as the source.

    Counter Without the file, tick 0 behaves exactly as it does today — guessing the gate and probing a worktree.

  • A configuration that has gone stale is noticed rather than believed.

    Check spec.config.json records measured_at and the commit it was measured at. If any dependency manifest or lockfile has changed since that commit, tick 0 re-runs the gate once and reports the difference before dispatching.

    Counter If nothing relevant changed, tick 0 does not re-measure — the config's whole point is that it is cheap.

B · A spec is written, not generated

new-spec6 criteria

  • /new-spec foo produces exactly one file, in a place you could have predicted.

    Check The file is specs/<nnnn>-foo.spec.html, where nnnn is the highest existing number plus one, four digits.

    Counter /new-spec Foo Bar! yields 0002-foo-bar.spec.html — no spaces, no punctuation, no second file anywhere.

  • The "Today" section describes the code as it is, from having looked at it.

    Check Every bullet under "Today" cites a file with a line number, or a command with its actual output. The cited lines exist and say what the bullet claims.

    Counter For a topic with nothing in the repo yet, the section says so in one line instead of describing something invented.

  • Every criterion in the document names a way it could fail.

    Check Each li.crit carries a p.check naming a file, a command, an input and an expected output, and a p.counter naming the case that must not trigger.

    Counter A claim whose failure cannot be named — "works correctly", "is fast enough" — does not appear as a criterion at all. It appears under Open questions, where it counts toward nothing.

  • Every decision the interview settled is in the document with its reason, and only the decisions that changed something are.

    Check Each li.decision holds the decision and a .why, and names at least one criterion id it changed.

    Counter A question whose answer changed no criterion is not recorded as a decision — so the section cannot be padded with agreement.

  • A spec is one file you can send to someone.

    Check The file references no external host except fonts.googleapis.com and fonts.gstatic.com: no <script src>, no stylesheet link to a sibling file, no remote image. Opened from disk with no server it renders complete; published as an Artifact it renders in light and dark.

    Counter It carries no <!doctype>, <html>, <head> or <body> tag — those break the Artifact wrapper, and browsers supply them anyway.

  • Spec and dashboard read as one system, from one source.

    Check The colour tokens exist exactly once in the repository: grep -rn -- '--ground:' --include='*.py' --include='*.html' --include='*.css' . outside specs/ returns one file, and both the dashboard generator and the spec template read from it.

    Counter A generated dashboard.html and a generated *.spec.html still each contain the full style inline — sharing a source must not make either of them depend on a file at view time.

C · The document is the register's source

runspec.py4 criteria

  • The register is parsed out of the spec, not re-worded out of it.

    Check runspec.py init --from-spec specs/0001-spec-workflow.spec.html writes a register with exactly as many criteria as the file has li.crit elements (18), each with id, criterion, check, reachable, complexity, seam, depends_on — ids and chips from the data- attributes, prose from the text of .sentence, .check and .counter, with the label spans (.k) excluded — measured: a parser that keeps them writes "Check With specs/…" into every register entry. Standard library only (html.parser suffices; getpos() gives the line for errors).

    Counter An li.crit missing a data-id or a .check aborts with the element's position named. It is never skipped quietly — a criterion that vanishes at parse time is the one failure mode that looks like success.

  • A broken graph fails at parse time, not six ticks later.

    Check A data-depends pointing at an id that does not exist, or a cycle, makes --from-spec exit non-zero naming the ids involved — before any run directory is written.

    Counter A valid graph passes, and runspec.py status reports the same READY NOW set it would have for a hand-written register.

  • A parsed criterion still has to be measured before it counts.

    Check Every criterion from --from-spec lands as open. Tick 0 then runs the "was this already true?" pass and, where it was, sets met with evidence and flags it in the report as already true — not as progress this run made.

    Counter No criterion is ever written as met by the parser itself, whatever the HTML says.

  • When measurement contradicts the spec, the contradiction is visible and the spec file is untouched.

    Check The disagreement lands in the register as corrections[] — original wording, measured value, reason — and appears on the dashboard. During the run git status --short specs/ stays empty.

    Counter The closing report proposes the patch to the spec file and does not apply it. A run that edits the document it is judged against cannot be judged.

D · Three skills, one install

packaging2 criteria

  • One install command makes all three commands available, and a stale hand-installed copy is called out by name.

    Check After ./install.sh, /spec-init, /new-spec and /run-spec are all available in a fresh session and resolve to this checkout.

    Counter Given a ~/.claude/skills/run-spec that is a real directory rather than a symlink — construct one — it still deletes nothing, but names the path to move aside and the command that does it. Today it refuses without saying how, and an outdated copy ran here for a week because of it.

  • The specs folder can be read at a glance from the command line.

    Check runspec.py specs lists each specs/*.spec.html with its number, title, criterion count and run status — no run / running / n of m met — resolved against ~/.claude/runs/<project>/.

    Counter In a project with no specs/ it says so and exits zero, rather than raising.

Decisions

HTML is the format /new-spec writes; Markdown stays readable input for run-spec. Because one file can be both the document a person reads and the structure a parser reads — and it publishes as an Artifact without a build step. Changes B05, C01.
Every machine field appears exactly once, as a data- attribute, and the page renders it with content: attr(). Because a value written twice — once for the eye, once for the parser — drifts, and the drift is invisible until a run acts on the stale half. Changes C01.
The spec lives in the repository; run state does not. Because a spec is source — reviewed, diffed, blamed — while a register is state, and mixing them is what the "no foreign checkout gets polluted" rule was protecting against. Changes A01, C04.
run-spec never edits a spec file during a run. Because a run that rewrites the document it is judged against cannot be judged. Corrections go to the register and are proposed as a patch at the end. Changes C04.
A parsed register starts entirely open. Because "a register that starts at 40 % green because nobody looked is a lie with a head start" — and a machine-readable spec makes that lie cheaper to tell. Changes C03.

Open questions

One run per spec, or one run spanning several? Leaning one-to-one: the register's percentage means nothing if its source is two documents. But a spec that turns out to be three runs has no way to say so yet.
What happens to a spec once its run closes — a status in the file, a move to specs/_done/, or nothing? Anything written back into the file conflicts with the decision above. Nothing is the honest default until the closing report has proven it needs more.
Should /spec-init write a section into the project's CLAUDE.md? It would make the workflow discoverable to every session. It also edits a file the project owns, on a first run, which is exactly the kind of thing that makes people distrust a tool.
Can /new-spec convert an existing Markdown spec instead of interviewing from scratch? Useful, and the fastest way to a bad register: the conversion would inherit claims nobody can name a failure for. If it happens, it interviews about those claims rather than transcribing them.
Is content: attr() the right call for the seam paths, which a reader may want to copy? Generated text is not selectable in most browsers. The single-source rule is worth more than copyable paths — but this is the criterion most likely to be overturned by someone actually using the document.
